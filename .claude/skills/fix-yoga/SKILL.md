# 角色与目标

你是《瑜伽师地论》译文修复 Agent。任务是根据 `output/{N}.check.md` 中记录的校对问题，逐条判断修改意见是否成立：成立则改写对应译文段并替换到 `output/{N}.md`；不成立则不修。最终生成 `output/{N}.fix.md` 修复记录。

**核心原则：有问题才修，没问题不强行修。** LLM 判断每条意见是否成立，存疑即拒绝。

# 架构设计

```
prepare_fix.py  ->  fix_{N}_pairs.json + fix_{N}_batch*.json  ->  [LLM 逐条判断]  ->  fix_{N}_batch*.json (verdicts)  ->  apply_fix.py  ->  output/{N}.md (更新) + output/{N}.fix.md
```

- `prepare_fix.py`：从 `output/{N}.check.md` 解析问题列表，从 `output/{N}.md` 提取「原文段->译文段」对，按批切块（每批 10 条）。**不做任何质量判断**。
- LLM：读取每批的**全量原文/译文/问题/建议**，逐条判断修改意见是否成立，成立则改写译文。**判断与改写全部由 LLM 完成**。
- `apply_fix.py`：合并各批判断 -> 应用 ACCEPT 的修复到 `output/{N}.md` -> 生成 `output/{N}.fix.md`。

# 段落定义

与 check-yoga 完全一致：
- 段落对 = `output/{N}.md` 中「以 `　　` 开头的原文段（可多行颂偈）」+「紧跟其后的以 `*` 开头的译文段（可多行）」
- 段落号与 `output/{N}.check.md` 中的「段落 N」严格对应
- 颂偈多行译文有两种合法格式：① **整块跨行 `*...*`**；② **每行独立 `*...*`**。修复时必须保持原格式。

# 判断与改写纪律

## 判断标准（按 type 分别校验，详见 AGENT_INSTRUCTIONS.md）

| 代号 | ACCEPT 条件要点 |
|------|------|
| NEAR-COPY | trans 确实超八成句子原词原句、保留古文虚词/语序；能产出实质白话化的改写 |
| MISSING | trans 确实为空 |
| VERSE-NOT-TRANSLATED | 原文为颂偈且 trans 照抄原文；能译为有韵律白话 |
| FORMAT | trans 整体未以 `*` 包裹 / 含"译文"前缀 / 标题被翻译。**注意**：颂偈多行格式 A 与 B 均合法，不得误判 |
| ERROR | 经核对原文 trans 确实误译/漏译/术语错误，且 suggestion 纠正正确 |
| OTHER | trans 确实不通/失真/矛盾；能产出更好的译文 |

## 改写硬性要求

1. **忠实原文**：不增义、不减义、不歪曲。无把握时保留古文表达，不要凭空意译。
2. **白话化**：除「可保留专有名词清单」外，古文句式一律改写为白话。
3. **专有名词清单**：阿赖耶识、三摩呬多地、补特伽罗、那落迦、嗢拖南、萨迦耶见、奢摩他、毗钵舍那、等无间依、俱有依、种子依、羯罗蓝、健达缚、预流果、一来果、不还果、薄伽梵。**清单外术语一律白话化**（如"苾刍"->"比丘"）。
4. **格式保持**：new_trans 必须与原 trans 同格式（单行 `*...*` / 多行格式A / 多行格式B）；颂偈原文 N 行 -> new_trans 也 N 行。
5. **首尾包裹**：new_trans 必须以 `*` 开头且以 `*` 结尾。
6. **无前缀**：不得添加"译文""翻译""译"等前缀。

## 修复 FORMAT 时只改格式不改译文

FORMAT 问题的 new_trans 与原 trans 文字相同，仅 `*` 包裹调整。

# 自动化执行工作流

## 步骤一：准备（确定性脚本）
对每个目标文件 `N`：
```
python3 .claude/skills/fix-yoga/prepare_fix.py <N>
```
- 解析 `output/{N}.check.md` 提取问题列表
- 从 `output/{N}.md` 提取段落对
- 生成 `fix_{N}_pairs.json`（所有问题 + 原文 + 当前译文）和 `fix_{N}_batch*.json`（每批最多 10 条问题，含完整上下文）

**批次大小**：10 条/批。修复判断需逐条对照原文/译文/建议改写，认知负荷高于校对，取 10，避免单 Agent 上下文过长导致后半段草率判断。

若 `output/{N}.check.md` 显示「本文件无需修改」（无问题段落），跳过该文件。

## 步骤二：并行派发判断子 Agent

**关键**：所有批次必须在同一轮消息中并行派发，确保每个子 Agent 独立判断，互不干扰。对文件内每批派发一个子 Agent（`subagent_type: general-purpose`），prompt 精简（指令在 AGENT_INSTRUCTIONS.md，子 Agent Read 一次命中缓存）：

```
读取 .claude/skills/fix-yoga/AGENT_INSTRUCTIONS.md 获取修复判断指令，按其要求判断并改写。

批次文件：fix_{N}_batch{batch_num}.json
输出文件：fix_{N}_batch{batch_num}.verdict.json
```

**输出与输入分离**：子 Agent 读取批次文件后，将判断结果写入 `.verdict.json`（与输入文件同名但扩展名不同）。原始批次文件保留，便于子 Agent 失败时重试--只需重新派发该批次，子 Agent 再次读取原批次文件即可。

**上下文衰减控制**：单文件问题数较多时，每批 ≤ 10 条、每批独立子 Agent，避免单个 LLM 上下文过长导致后半段判断质量下降。

## 步骤三：应用修复 + 生成报告

所有子 Agent 完成后，运行：
```
python3 .claude/skills/fix-yoga/apply_fix.py <N>
```
- 合并各批 `.verdict.json` 中的 verdicts
- 对每条 ACCEPT 进行**格式校验**（`*` 包裹、颂偈行数匹配）--校验失败的标记为「校验失败」不应用
- 对校验通过的段落：定位 `output/{N}.md` 中对应译文块并替换为 new_trans
- **MISSING 情况**（原文段后无译文块）：在原文段后插入 new_trans（含前后空行）
- 生成 `output/{N}.fix.md` 修复记录

**JSON 容错（三段修复）**：verdicts 文件是 LLM 生成的 JSON，可能因值内含 ASCII 双引号/换行未转义而解析失败。`apply_fix.py` 依次尝试：① 直接 json.load；② 按段落号键切分后对每个对象单独 json.loads；③ 字段级正则提取。某批次三种方式都失败时，该批段落标记为「批次解析失败」并在报告中列出，不影响其他批次应用。

**段落定位**：按段落号（与 check.md / prepare_check.py 同一序号体系）在 `output/{N}.md` 中定位原文段（`　　` 开头），找到其后紧跟的译文块（`*` 开头，可能跨多行），整体替换。从后往前替换以避免行索引偏移。

**格式校验**：对 ACCEPT 的 new_trans 校验：
1. 以 `*` 开头且以 `*` 结尾
2. 颂偈原文 N 行 -> new_trans 也必须 N 行（格式 A 与 B 行数一致）
校验失败的不应用，标记为「校验失败」。不强制格式 A/B 与原 trans 一致（check-yoga 视两者均为合法）。

报告格式：
```markdown
# output/{N}.md 译文修复报告

- 修复时间：<日期>
- 校对问题数：X
- 成立并修复：Y（占 Z%）
- 不成立：A
- 校验失败：B
- 应用失败：C
- 批次解析失败：D

## 修复记录

### 段落 8 【近似未翻译】 ✅ 已修复

- **原文**：……
- **原译文**：……
- **校对问题**：……
- **修改建议**：……
- **判断依据**：trans 后半段「若好的显色……」确为原词原句照搬……
- **新译文**：……

### 段落 99 【其它质量】 ❌ 不成立，未修复

- **原文**：……
- **原译文**：……
- **校对问题**：……
- **修改建议**：……
- **判断依据**：trans 已实质白话化，problem 过度挑剔……

### 段落 134 【译文缺失】 ✅ 已修复

- **原文**：……
- **原译文**：（无）
- **校对问题**：原文段后没有译文。
- **修改建议**：补译此段。
- **判断依据**：trans 确实为空，补译……
- **新译文**：……

### 段落 200 【近似未翻译】 ⚠️ 校验失败，未修复

- **原文**：……
- **原译文**：……
- **校对问题**：……
- **判断依据**：……

## 汇总
- 总问题数：X
- 已修复：Y
- 不成立：A
- 校验失败：B
- 应用失败：C
- 批次解析失败：D

按问题类型统计：
- 近似未翻译（NEAR-COPY）：已修复 a / 不成立 b / 校验失败 c
- ……
```

若某文件**完全没有校对问题**（check.md 报告"无需修改"），fix.md 输出：
```markdown
# output/{N}.md 译文修复报告

- 修复时间：<日期>
- 校对问题数：0

✅ 校对报告未发现问题，本文件无需修复。
```

## 步骤四：清理
删除临时文件：`fix_{N}_pairs.json`、`fix_{N}_batch*.json`、`fix_{N}_batch*.verdict.json`。

# 大文件处理

- 每文件问题数由 `prepare_fix.py` 输出决定批次数量。
- 批次在文件内、以及多个文件之间均可并行派发。
- 单文件批次较多时（>8），分批派发（如每轮 8 个），避免一次性并发过多。

# 交互反馈

- 启动时，简要确认修复的文件范围。
- 派发后保持静默高效。
- 完成后告知每文件的修复统计（成立 X 条 / 不成立 Y 条）。
- 结束时输出简明报告：修复文件数、应用修复总数、拒绝总数。
